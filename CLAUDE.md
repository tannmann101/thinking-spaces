# CLAUDE.md — Thinking Spaces

## What this is
A personal, single-user thinking workshop app. Each train of thought (a concept, theory, plan, assessment) becomes a "Space" — a revisitable, evolving place, not a static note. Spaces can hold different kinds of content depending on what they're for, can reference each other, and the whole system should feel alive and buildable-on-itself over time. This is being built for one person's own use, not as a product.

## Non-negotiable working method
This project has a specific failure mode to avoid: past attempts sent one big prompt, got a rough MVP back, then spent a long time fighting it in frustrating, unreviewable tinkering. That is not how this build happens. Instead:

- **Work in small, reviewed slices.** Finish one coherent piece, then stop and explain in plain language what was built and why, before continuing.
- **Confirm scope before starting any new pass or major piece of work.** Restate your understanding of what's being asked; don't assume and run.
- **No black boxes.** The person directing this project is not writing the code themselves. Every feature needs to be legible to a non-implementer: centralize things that would otherwise be scattered (a single registry file for Tools, a single registry file for Views — see below), comment intent not just mechanics, and avoid clever abstractions that hide what's actually happening.
- **Favor boring, readable code over clever code.** This is a solo-maintained personal project, not a codebase optimized for a team.
- **Don't build ahead of the current priority** (see Roadmap) without explicit go-ahead, even if the next piece seems obvious or easy.
- **Use the person's own vocabulary** (Dashboard, Creation Mode, Spaces, Tools, Resources, Categories, Workspaces, Dev Mode, Relational Map, Work, Synthesis, Provenance — see below), not implementation jargon, when discussing the app with them. If a term drifts from how they actually think about it, that's a signal to realign the language, not just push forward.

## Tech stack
React + Vite (frontend), Node/Express + SQLite (backend). This matches the person's other personal apps (a household finance tracker, a household-management app called Secretary) — consistency across their own tools matters more than any particular technical advantage. This remains the primary stack for local development (see the launcher/README.md and the root README.md) -- `worker/` is a second, deploy-only backend (see "Hosting" below), not a replacement for `backend/`.

## Hosting
The app now has a real hosting path, matching how the person's other domain (`thegardners.xyz`, home to their "gardners-hub" household site) is already set up: static frontend on GitHub Pages, a Cloudflare Worker for anything needing a backend, gated by the same Cloudflare Access PIN login the rest of that domain already uses. Confirmed via direct question over the alternative (keep the Express/better-sqlite3 backend as-is, deploy it unchanged to a host like Render/Fly with a persistent disk, and have a Cloudflare Worker just proxy to it) -- the person picked the fuller Cloudflare-native port once shown the real cost picture (Render/Fly both dropped their free persistent-disk tiers in 2024-2026, so the proxy option would run ~$7-8/mo forever; the full port is free indefinitely, matching gardners-hub's own economics, at the cost of a real porting project rather than a quick deploy).

`worker/` is that port: a Cloudflare Worker + D1 (D1 is Cloudflare's serverless, SQLite-compatible database) reimplementation of every route and query function `backend/` has, kept as a parallel, independently-runnable backend rather than a replacement -- `backend/`'s Express + better-sqlite3 code is untouched and stays the one used for local development (the desktop launcher, `npm run dev`). Structure mirrors `backend/src/db/queries/` file-for-file (`worker/src/db/*.js`, one module per concern), and `worker/src/index.js` is a single hand-rolled router (no Express inside a Worker) matching every route in `backend/src/routes/*.js` exactly -- same paths, same validation, same status codes. Every function takes `env` as an explicit first parameter (for `env.DB`, the D1 binding) rather than reading a module-level `db` singleton the way the Node backend does, since a Worker has no safe place to stash a per-request value at module scope -- the same pattern gardners-hub's own Worker already uses. D1 confirmed to support the JSON1 SQLite extension (`json_extract`/`json_each`/`json_array_length`) before porting began, since dozens of queries here depend on it.

Two of the Node backend's one-time startup migrations were deliberately *not* ported: `migrateTextBlockLines`/`migrateWorkItemSupport` upgrade rows written before their respective content shapes existed, but a D1 database starts fresh on the *current* shapes, so there's never a legacy-shaped row to migrate. `ensureTestSpaceExists` and `seedTemplates` were also pulled out of runtime code -- a Worker has no boot hook to run them at, and running idempotent existence-checks on every request would mean real extra D1 queries on every single request forever, for something that only ever needs to happen once. `worker/schema.sql` declares the finished current schema directly (no incremental `ALTER TABLE` history to replay), and `worker/templates-seed.sql` (generated programmatically from the real `TEMPLATES` array in `backend/src/db/seedTemplates.js`, not hand-transcribed, to rule out transcription drift) seeds the 6 built-in Templates -- both applied once via `wrangler d1 execute` during deployment setup, the same one-time-setup pattern gardners-hub's own `worker/DEPLOY.md` already established for its own schema/seed. The Test Space's actual demo content (`seedTestSpaceBlocks`) is deliberately *not* ported as generic seed data at all -- this is a migration of the person's own real, already-accumulated Thinking Spaces database, not a fresh install, so the real Test Space and every other real Space need to come from an export of their actual `backend/data/thinking-spaces.sqlite` file (not yet done -- see Open).

Verified live end-to-end via `wrangler dev` against a local D1 (Miniflare) emulation, exercising every single route by hand with curl -- not just the query modules in isolation: creating a Space from a Template (confirms `applyTemplate`/Skeleton-lane seeding), the full `=`/`?`/`!` shorthand-promotion path (the skeleton.js/trail.js circular pair, the most delicate part of the port), filing a line into a lane, pairing a Tension, Workspace create/assemble/report/delete, Work items and the cross-Space picker, all three Report levels, Insights' five facets, the Week calendar, the Graph, Reviews (draft + create, including the `sinceDate` ISO-normalization fix), Creation Mode's full `extraBlocks`/`workspaceNames` resolution path, every validation/404 error path, and the Test Space's delete-protection -- confirmed the local D1 database returned to just the Test Space after every test Space created during verification was cleaned up.

## The shape of the app, in plain language

This is the vocabulary to use — it's the person's own mental model, and it should stay the primary way of talking about this project:

- **Dashboard** — where you land: create Spaces, see Spaces, see trends/metrics/insights across them.
- **Creation Mode** — the flow for starting a new Space: pulling in Tools and Resources for what this Space is for, with real room for customization/personalization so the Space feels like its own thing, not a generic form.
- **Spaces** — one Space per train of thought. Every Space loosely falls into one of 5 starting clusters (see below), plus "Other" for anything that doesn't. A Space is never *just* its cluster, though — it gets tailored the way every train of thought is different.
- **Tools** — the functions/features a Space can use to work toward its purpose (write a paragraph, keep a checklist, compare two things, chart progress, etc.). Tools are internal to the app, modular and general-purpose, expanded in dev sessions like this one rather than built by the person from inside the running app. They should be visible as a catalog (with a demo of what each one offers) and some should be markable as "groupable" with others they work well alongside.
- **Resources** — anything that exists outside of (or alongside) the app that gets surfaced *within* it, in relation to a Space, a Relational Space, the Dashboard, or a Tool: a book, a computer, a phone, an account, a YouTuber or podcaster, a social media post, a discussion, a set of notes, an interpretive **lens** (etymology, phenomenology, anthropology, history, epistemology, philosophy, or any other reading discipline worth having on hand across many different phenomena, not just one) — anything worth having on hand while thinking something through. Creating one is a deliberately different flow from creating a Space (its own "+ New Resource" entry point on the Dashboard, not a cluster card inside ordinary Creation Mode): it homes in on what the Resource actually *is*, what it *affords*, what it *touches / is touched by* (real References to existing Spaces, picked at creation), and what it *offers* — those four facets become the new Resource's starting Categories, so it never starts as an undifferentiated blank page the way a generic Space's Text/List dropdown used to feel. A **Resource Template** (see the Roadmap entry below) can replace the first three of those four with a set tailored to a specific type of thing — a Book's own questions are different from a Riddle's — while the fourth (Touches / Touched By) stays the same for every type, since it's a mechanical capability, not a description. Under the hood it's still an ordinary Space (tagged `"resource"` plus any freely-chosen type tags like `"book"`/`"person"`/`"account"`), which is what gives it full, unconditional access to every other Tool/View/Category/Reference/Trail/Graph/Log capability for free.
- **Categories** — freely-named facets *of a single Space's own topic*, defined per-Space (e.g. a Space about a big purchase might have "Financial Impact," "Risk Tolerance," "Timing"). Distinct from tags, which categorize a Space itself among every other Space (e.g. "resource"). A block can belong to zero, one, or several Categories at once — a Space is trying to catch the pattern of something with several angles at play simultaneously, not sort its content into single, exclusive bins. Categories are managed on the Space page and assigned to blocks there (including right when a block is added); a filter strip lets you focus on one Category at a time without hiding a block's other memberships.
- **Workspaces** — a deliberately assembled, named environment *inside one Space* that bundles whichever Tools belong together for focused, hands-on work — distinct from a Category (a free-standing facet name with no page of its own; a lens on the existing feed) and distinct from a plain Tool/block (one single thing). A Space can have several Workspaces; a Tool can belong to any number of them, or none, and stays visible in the ordinary flat feed either way — joining a Workspace is additive, never a move. Opening one is a real "pop into a tool-specific environment" moment: its own dedicated page, not an inline row, where its assembled Tools get room to work together. Creating/naming/deleting a Workspace, and adding or removing a Tool from one, are all ordinary, always-available actions, same as anything else in this app — no separate mode to switch into, which is what keeps this consistent with the Dev Mode decision below despite Workspaces being reached by navigating to their own page (the same kind of break the Template editor or the Graph page already are, not a gate on ordinary editing).
- **Dev Mode** — **resolved, no longer a distinct mode.** Earlier brainstorming described a separate mode you'd enter to make structural changes. The person overrode that directly: everything should be addable/removable/editable in place, on every page, all the time — a toggle you have to switch into runs against that. So "Dev Mode" now means *ordinary, ubiquitous editability*, not a gate: structural controls (add/remove/reorder Tools, edit any property) are always visible, everywhere, never hidden behind a switch. Workspaces (above) introduced a genuine dedicated page you navigate to for focused work with a Tool — deliberately reconciled with this decision, not a quiet reversal of it: nothing on the ordinary Space page became less editable in place to make room for it.
- **Relational Map** — where Spaces get connected: simply (checkboxes/text references) and visually, as an interactive node/link thought-map in the spirit of Obsidian's graph view, but livelier. This is also where Relational Spaces (a Space seeded from several others) get managed. A Relational Space is tagged `"relational"` at creation (see `createRelationalSpace` in `backend/src/db/queries/spaces.js`) — an ordinary, freely-removable tag, the same pattern a Resource's `"resource"` tag and a Synthesis's `"synthesis"` tag already use, added by the category-hygiene audit below once it surfaced that a Relational Space previously had no persistent signal at all once created (no origin, no tag) and so was indistinguishable from a Space built by hand the moment you left the Graph page.
- **Log** — a global, cross-Space activity feed: every Space/Tool/Template created or removed, every status change, merged with each Space's own Trail history, in one chronological place — meant as the foundation for trends and data insights over time, not just a record for its own sake.
- **Work** — the individual acts of thinking a Space is for (assess, question, and more to come) each become their own real Tool, not a generic block with a label. An Assessment is a judgment with supporting rationale and a confidence marker; a Question is an open inquiry with why it matters and how central it feels. Every kind of Work shares that same underlying shape, which is what lets Synthesis (below) pull from them uniformly — but each still reads as its own distinct Tool in the catalog, not a labeled Text block.
- **Synthesis** — compiling a handful of existing Work items, possibly from different Spaces, into a new, more polished piece: an essay, a definition, a story, a plain writing entry. Its own guided flow, reached from its own "+ New Synthesis" entry point on the Dashboard (next to "+ New Resource") — under the hood it's still an ordinary Space (tagged "synthesis" plus an optional freely-chosen kind), pre-seeded with the selected items' own text copied into a starting block to draft from, plus a Reference back to each source Space.
- **Provenance** — whether a Space was brought in from *outside* the app (a Resource — a book, a person, an account) or *produced by the app itself* through thinking done here (a Synthesis, or a Space later judged mature enough to cite elsewhere). Shown as a small badge (External/Internal) on the Space page and in the Dashboard's digests. A mature Synthesis can be explicitly **promoted** to also carry Resource status once it's settled enough to be referenced the way an external Resource is — promoting never changes what a Space *is* (its provenance stays "internal" forever), only that it's now also discoverable as a Resource. This is the app's answer to "Spaces can produce things which turn into tools/resources down the line": Work produces claims, Synthesis compiles them into a real piece, and promotion is the last, optional step that lets a finished piece take its place alongside everything sourced from outside.
- **Insights** — the fuller realization of the Dashboard's founding promise to "see trends/metrics/insights across [Spaces]." Its own dedicated page, made deliberately prominent (a banner on the Dashboard, not just a nav link), reading four facets across every Space at once: what kind of thinking is happening and how settled it feels (Work Type and confidence mix), what themes keep recurring and which conflicts in your own reasoning are still open (recurring Categories, open Tensions), whether thinking is actually moving and which Spaces have gone quiet (weekly activity, staleness), and how much of what exists was brought in versus produced, and how much of that raw thinking has actually been distilled (Provenance split, the Work → Synthesis → Resource funnel). Purely computed from existing data -- no new schema, no new stored fields.
- **Reports** — the single-thing complement to Insights' cross-Space trends: any Space, any Workspace, or any one Tool/Work item (a Hypothesis, a Text block, whatever) can produce a structured-plus-prose snapshot of its own current state, on demand, via an ordinary "Report" button right where that thing already lives -- no separate mode or page. Meant as raw material for two different audiences: Insights already covers the aggregate/trend reading, while a single report is meant to be copied out of the app entirely and handed to an external Claude conversation that can give one Space/Tool/thought closer attention than an in-app view ever could. A Relational Space and a "connection" between two Spaces don't get their own report kind -- a Relational Space is just an ordinary Space (so the Space report already covers it), and a connection is just a Reference block (so the block report already covers that). Purely computed on demand, nothing stored or versioned.
- **Time** — the practical-utility side of the app, threading together everything to do with when: a due date, a checkpoint, actually timing work, looking back on it, and finally seeing all of it in one place. A whole arc, all four layers now built: a real due date on a Space, a Milestone as its own real Tool (a checkpoint with a target date and a reached/not-yet-reached state, distinct from a List item's `reviewBy`), a Session as another real Tool (a timed sitting of work you start and stop, with the elapsed time logged), a Review -- a deliberate, structured look-back at what changed since the last one, reusing Reports' "diff what changed" idea but scoped to "since last Review" instead of "right now," and reusing Trail's own storage rather than inventing a parallel history -- and a fifth Insights facet pulling all three together with due dates: what's coming up, what's overdue, how much time has actually been logged, and which Spaces have gone quiet on reflection specifically, not just on activity in general.
- **Projects** — a real, named goal/project inside one Space that a Milestone or a Session belongs to, the Time family's own dedicated structural concept (like a Workspace, but for the two Time Types specifically) rather than either Tool only loosely implying structure on its own. Named "Project," not "Goal," to avoid colliding with a Space's own pre-existing `goal` field ("Working toward" -- what the Space *as a whole* is working toward, a single free-text line; a Project is a real, separate thing several Milestones/Sessions can belong to at once). A Milestone or Session belongs to at most one Project at a time (unlike a Tool's many-to-many Workspace membership), since a checkpoint or a timed sitting most naturally serves one project. Reached from a "Projects" section on the Space page (next to Workspaces), its own dedicated page shows every Milestone/Session assigned to it plus a computed progress line (Milestones reached, minutes logged across Sessions), and lets you add a new Milestone or start a new Session directly into it. Starting a Session got its own one-click "▶ Start a Session" affordance too -- on the Space page and on a Project's own page -- instead of only the generic "+ Add Entry" dropdown, since starting a timer is a more time-sensitive action than adding an ordinary entry. A Project card carries its own visual identity (a gold `--accent` left-edge stripe, the same "General neutral / Work maroon / Time gold" family-color convention `.block-row[data-family]` already uses) rather than reading as an unlabeled Workspace twin -- see the Roadmap entry below for the audit that surfaced this and the other parity gaps it closed (a Project-level Report, a `Projects:` line in a Space Report's Structure section, and real Graph nodes/edges).

### Where the build actually stands against that vocabulary

Passes 1–5 of the original roadmap are done, plus a visual-polish pass, an editability pass, a Tools catalog, a Creation Mode overhaul, and the Dev Mode decision above. Mapped onto the language:

- **Tools** = the **Block types** (Text, List, Reference, Media, Comparison) and **View types** (Timeline, Progress, Streak, Ledger, Graph), registered in `frontend/src/registry/blocks.js` and `frontend/src/registry/views.js`. Browsable at `/tools` (`frontend/src/pages/ToolsPage.jsx`) — every Tool's description, a live demo (via each registry entry's `demoBlock`/`demoProps`), and `worksWith` for what it pairs with. (As of the vocabulary-audit pass below, "Block" was never actually chosen from the person's own vocabulary — it was implementation language typed during construction. What the UI now shows for one is **Entry**, and the Text Tool's UI label is now **Writing**, a Skeleton "lane" is now a Skeleton "section" in visible copy. This was confirmed a copy-and-labels-only rename: the registry key `text`, every `*Block.jsx` component/file name, `blockRegistry`, the `blocks` table, `block.type`, and every JSON field name — `skeletonLane` included — all keep their original names, since nothing about the code itself was wrong, only what a person reads on screen. The rest of this document keeps describing the code using its original names, since those are what's actually in the source.) A Block's registry entry also carries `family` (`'general'` or `'work'`, added once the registry grew to 15 Block types and both the catalog and the "+ Add Block" dropdown had become one flat, hard-to-scan list) — the catalog groups by it under "Blocks" (General/Work sub-headings) and `NewBlockForm.jsx` groups by it via native `<optgroup>`s, so a future Work Type needs only its registry entry, no edit to either UI. A Block's registry entry can also carry an optional `workshopComponent` — a bespoke, more spacious version of the Tool that a Workspace page (see the Workspaces vocabulary entry) renders instead of the ordinary `component`, when one exists; most Tools don't have one yet, and fall back to `component` until they get their own redesign pass. **Text** is the first: `frontend/src/blocks/TextWorkshop.jsx` (registered as `text.workshopComponent`) is a real writing environment in place of the small click-to-edit paragraph — always-open, an auto-growing serif writing surface, a live word count, the `quote`/`paraphrase`/`reflection`/`inference` attribution tag made actually settable for the first time (it existed in the data model with no UI anywhere before this), and a rendered "as it reads" preview with wiki-links resolved underneath the raw draft. It deliberately still saves on blur rather than continuously while typing — the `=`/`?`/`!` Skeleton-promotion path (see `saveTextBlockWithPromotion`) rewrites a block's own text out from under it when a line gets promoted, and a background autosave racing that or an in-progress keystroke risked either lost input or a resurrected already-promoted line; one discrete commit per editing session avoids that. The `[[Space]]` link-rendering logic (`renderTextWithLinks`) was pulled out to `frontend/src/blocks/textLinks.jsx` so the ordinary inline Text block and the Workshop version share one implementation instead of two copies drifting apart. **List** is second: `frontend/src/blocks/ListWorkshop.jsx` (registered as `list.workshopComponent`) turns the compact, run-on-line-per-item feed row into a card per item, with real drag-and-drop reordering (native HTML5 DnD, not a hand-rolled pointer tracker -- a plain linear reorder doesn't need the Graph's freeform physics) in place of up/down buttons, and each item's secondary fields (confidence, date, review date, number) as their own small labeled chips instead of run-on inline dashes. It also closes a real gap: a list that starts empty could never gain a checkbox/confidence/date/number field, since a new item's shape was only ever inferred from an existing item -- the Workshop's empty-list shape picker lets the very first item establish that shape explicitly. The item-shape inference logic (`buildNewItem`, `CONFIDENCE_CYCLE`) was pulled out to `frontend/src/blocks/listItems.js`, same reasoning as `textLinks.jsx`, so the ordinary inline List block and the Workshop version can't drift apart on what shape a new item gets. **Reference, Media, and Comparison** followed together in one pass: `ReferenceWorkshop.jsx` gives the note a real auto-growing surface and the trust rating a clear chip row (`unrated`/`high`/`medium`/`low`), plus a live preview card of the target Space itself (title, status, goal, Categories, tags, fetched fresh via `getSpace`) -- so "what this touches" actually shows something about what it touches, not just a name to click through to. `MediaWorkshop.jsx` adds a larger click-to-zoom lightbox and, closing a real gap, an editable source URL (previously a broken or placeholder image URL could never be fixed without deleting the block). `ComparisonWorkshop.jsx` gives each side its own card in a clearer side-by-side grid, a chip-style contrast toggle with a real auto-growing note surface, and a "swap sides" button; each side still renders through the ordinary `TextBlock`/`ReferenceBlock` (via the same `onSave` override they already supported for embedded, non-standalone content) rather than through `TextWorkshop`/`ReferenceWorkshop`, since those expect a real block id a Comparison side doesn't have. **TextWorkshop was substantially redesigned again in a later pass**, from one shared attribution tag for the whole block into discrete, individually-tagged lines: a Text block's content is now `{lines: [{id, text, tag}]}` rather than `{tag, text}`, so each line -- not just the whole paragraph -- carries its own `quote`/`paraphrase`/`reflection`/`inference` tag, set independently via a small margin glyph per line. Enter commits the line being edited and opens a fresh blank line after it; blur commits without adding one. The ordinary inline `TextBlock.jsx` stays deliberately simple about this: it still edits as one joined multi-line textarea and re-splits the result back into lines on save, matching each line to its old self by exact text (`relineFromText`) so an untouched line keeps its id and tag -- only a changed or new line loses its old attribution, which is the honest default (a changed sentence's old attribution may no longer be right). Comparison's embedded sides keep the older `{tag, text}` shape forever, since they're plain objects embedded in a `comparison` block's own content, never real `type='text'` rows -- `TextBlock.jsx` detects which shape it was handed (`legacy = !block.content.lines`) and renders either. Every Text block is created through one function, `createBlock` in `backend/src/db/queries.js`, which normalizes whichever shape it's handed into `{lines}` via a private `normalizeTextContent` helper -- so no frontend call site that creates a Text block (a Template, `ensureSkeletonLanes`, `NewBlockForm`, `CreateResource`, seed data) needed to change for this; a one-time `migrateTextBlockLines()` backfill (run at server startup) upgrades any pre-existing rows still on the old shape. TextWorkshop also gained Focus Mode (see the Workspaces entry below) and a per-line "File" action that copies a line's text into a Skeleton lane without removing it from the Writing Surface -- see the Skeleton entry below, a deliberately different verb and outcome from typed `=`/`?`/`!` shorthand, which still promotes a line out of the block entirely.
- **Spaces' 5 clusters** = originally the 5 built-in Templates (Inquiry/Analytical, Technical/Practical, Life Management, Person-Reflection, Creative), now 6 with **Problem Formulation** (see the Work vocabulary entry above and `backend/src/db/seedTemplates.js`) — each a named starting arrangement of Tools. "Start Blank" in Creation Mode already serves as the "Other" option. Problem Formulation seeds a blank Writing Surface, a "Lenses to Consider" List pre-filled with the person's own habitual reading disciplines (Phenomenology, Philosophy, History, Etymology, Anthropology, Epistemology, checked off as actually applied rather than required), and a blank Formulation block -- added the same way every prior Template addition has been, via `seedTemplates()`'s own idempotent per-id check, so restarting the server inserts just the new row without touching the existing 5 or requiring a fresh database.
- **Resources** = a Space carrying `"resource"` in its `tags` array (a plain JSON array on `spaces` — see Data model). Extra tags (`"book"`, `"person"`, `"account"`, `"lens"`, ...) already work for sub-typing with zero new code. Surfaced in the Dashboard's Resources digest and selectable in ordinary Creation Mode. The Visual Identity glyph (an organic branching mark per Space, computed from status/reference count/open tensions — never decorative) is real and themed to match. Widened in a later pass to react to two more already-computed dimensions, overdue status and Milestone-reached ratio — see the Roadmap entry below.

A fourth, deliberately different layer was added on top of those three computed dimensions in a later pass: a manual accent (`star`/`underline`/`triangle`/`dot`), hand-picked per-Space from a small chip-toggle picker on the Space page (`AccentPicker` in `frontend/src/pages/SpacePage.jsx`) and persisted as `spaces.accent`. `SpaceGlyph.jsx` draws it in its own color (`--accent`, a warm gold, distinct from the maroon the computed shape uses) so it always reads as an added mark, never a change to what the glyph is actually reporting about the Space — the manual layer sits *on top of* the computed base, it never replaces it. Since it's drawn inside `SpaceGlyph` itself, it shows up for free at every scale that component already renders at (the Dashboard card, the Space-page header) with no per-page work.

**Tool/section personality**, added in a later "professionalism pass" (see Roadmap): a grounded audit (screenshotting the real Tools catalog, a real Space page, the Dashboard) found that every Block type, every View type, and every Dashboard digest rendered as a visually identical box — differentiated only by reading its text, not by looking at it. Fixed with two additions to `blockRegistry`/`viewRegistry` (`frontend/src/registry/blocks.js` / `views.js`): `icon`, a single restrained text glyph per Tool (no emoji -- `¶` Text, `⚖` Assessment, `◆` Milestone, and so on for all 22 Tools), and the existing `family` field pressed into double duty as a coarse color grouping. Rather than invent a third hue, family color reuses what the palette already means: General stays neutral (the foundational, unmarked family), Work gets `--maroon` (the app's own primary color, fitting since Work -- the thinking-act Tools -- is literally the app's central activity), and Time gets `--accent` (the gold already reserved for Visual Identity's manual layer and for Time's own reached/running states, so this doesn't introduce a competing meaning for gold, it extends the existing one). Rendered as a left-border stripe on `.tool-card` (`ToolsPage.jsx`) and on every `.block-row` (`SpacePage.jsx`/`WorkspacePage.jsx`, via a `data-family` attribute read from the registry at render time -- no change to any individual Block component), plus a small `.block-type-tag` (icon + label) above each block in the feed. That tag closes a real, separate gap found in the same audit: a Work block's own kind (e.g. "Assessment" vs. "Question") was previously never rendered anywhere at all -- `WorkBlock.jsx`'s `statementLabel` prop was only ever used as placeholder-hint text, not a visible label. The same personality idea extends to the Dashboard's five digests (`Dashboard.jsx`): each gets its own icon and, for the two with an existing color meaning elsewhere, a matching accent -- Overdue for review borrows the same maroon `.overdue-badge` already uses (this *is* the same "overdue" concept), Syntheses borrows the gold Provenance already uses for "produced by the app itself." The other three digests (recent Trail activity, resurface suggestion, Resources) stay neutral, icon-only.

**Dialogs and interaction polish**, the professionalism pass's second slice: the app's only two calls out to native browser chrome (`window.confirm`, `window.prompt` -- 6 call sites in total) are gone, replaced by a themed `ConfirmDialog` (`frontend/src/components/ConfirmDialog.jsx`), mounted once at the app root (`App.jsx`) via a `ConfirmDialogProvider` and reached from any page through a `useConfirmDialog()` hook exposing `confirm(message)` (plain yes/no) and `promptToMatch(message, matchText)` (the same "type the name back exactly" pattern Space deletion already used, now themed and shared instead of duplicated). Both return a Promise, awaited at the call site the same way the native functions returned synchronously -- no page had to restructure its own delete-handler logic, just swap the call. Alongside it: the stylesheet had zero CSS transitions anywhere despite 27 `:hover` rules, so every state change snapped instantly -- one shared rule (`transition: border-color, background-color, color, opacity`) applied to every interactive element fixes that app-wide, respecting `prefers-reduced-motion`. A `:focus-visible` outline ring was also added site-wide (keyboard/assistive-only, invisible on a mouse click) -- the app previously had almost no visible keyboard-focus indication at all. The dialog overlay is the one deliberate `box-shadow` in the whole app -- a true overlay needs to read as elevated above the page behind it, which the app's otherwise-flat, shadow-free aesthetic doesn't achieve on its own; everything else stays shadow-free by design.

**Correctness fixes**, the professionalism pass's third slice -- the three real issues `oxlint` caught, not stylistic nits: `SessionBlock.jsx`'s `useState(Date.now())` called the impure `Date.now()` fresh on every render (harmless here since React only used the value once, at mount, but still wrong) -- fixed with the lazy-initializer form, `useState(() => Date.now())`. `LedgerView.jsx` built its running-total column by mutating a `let runningTotal` variable inside a `.map()` callback; rewritten with `.reduce()` building a new array each time, so there's no mutated variable for the linter (or a future reader) to worry has escaped its render scope, even though in this specific case it never actually did. `GraphView.jsx`'s several "ref accessed during render" warnings were investigated and left as-is, deliberately: `nodesRef.current` (holding every node's live x/y/vx/vy from the hand-rolled physics loop) is read in the render body on purpose, because the alternative -- copying the whole node array into `useState` on every animation frame just to satisfy the rule -- would mean a full React reconciliation pass 60 times a second for data React never needs to diff against anything. The physics loop's own `forceRender` call already guarantees a fresh render every frame the simulation runs, so nothing actually goes stale in practice; a comment at the read site now says so directly, so a future reader doesn't mistake the linter warning for an unexamined bug. The one genuinely free fix taken there: an unused `event` parameter on `onMouseUp` removed.

**An "expert-grade aesthetics" pass**, at the person's explicit request once the test suite was finished, "to make this almost industry-standard level legible/sensible." Grounded in a real audit before touching anything, matching every prior open-ended ask's method: screenshotted every real page at 1440px (Dashboard, Tools, Insights, Log, the Map, Templates, a Space page, all three Creation flows) and read through the whole of `index.css` (2,644 lines) rather than guessing. That audit found four concrete, independent issues; presented as a multi-select confirmation, three were chosen first, and the fourth followed once its own PR was up, at the person's explicit request to include it too. All four landed as a result, each small and self-contained:
- **A type scale.** `index.css` had drifted to 24 distinct font-size values with no defined steps, several only 0.5px apart (10.5px, 12.5px, 13.5px, 14.5px, 15.5px, 16.5px) -- reading as accidental rather than intentional at any of those sizes. Replaced with 13 named tokens (`--fs-2xs` through `--fs-5xl`) in `:root`, grouped by real, observed usage (tiny mono chip/badge text, small UI chrome, body-adjacent reading text, headings and large display numbers) -- `--fs-body-lg` (16px) deliberately matches `body`'s own default size, so ordinary reading text inside a card and the page's base text stay the same unless a component has a real reason to differ. Every one of the file's 132 `font-size` declarations now reads from a token. The border-radius split (27 uses of 3px, 25 of 2px) turned out, on inspection, not to be arbitrary at all -- small inline chrome (pills, chips, buttons, form controls) already consistently used 2px and larger surfaces (cards, panels) already consistently used 3px; the actual gap was that this convention existed only as muscle memory, never named, so a future addition could easily drift from it without anyone noticing. Named it instead: `--radius-sm`/`--radius-md`. Three deliberate exceptions (50% circles, one literal `0` for a square corner already commented as intentional, and two 4px radii on the app's two most attention-grabbing surfaces -- the Insights banner and the confirm-dialog overlay) were left as plain literals with a one-line comment each, rather than forced onto the shared scale.
- **Native control theming.** Two spots fell back to unstyled browser defaults inside the otherwise fully art-directed theme. The Tools catalog's Media demo (and any real Media block with no image) used a hand-authored placeholder SVG (`DEMO_IMAGE_SVG` in `frontend/src/registry/blocks.js`) hardcoded to a light-gray fill and black default-sans-serif text -- recolored to the app's own `--surface-2`/`--ink-faint` hex values and mono font (an SVG data URI can't read CSS custom properties, so the literal hex values had to be copied in directly, called out in the code's own comment). `MediaBlock.jsx` also had a real, separate gap the same audit surfaced: a Media block with an empty `url` rendered a raw `<img>` tag with no `src`, showing the browser's native broken-image icon -- now shows the same themed `.media-placeholder` treatment the audio/sketch stub types already used, closing the gap consistently rather than inventing a new pattern. Every `<input type="date">` (the Space page's Due field, a Milestone's target/reached dates) now explicitly sets `font-family: var(--mono)` (previously inherited whatever serif/sans context it sat in) and tints its calendar-picker icon via `::-webkit-calendar-picker-indicator` to match the app's dimmer ink tones -- `color-scheme: dark` on `:root` already got the browser to draw the field and its placeholder in a dark-appropriate palette, so this was the one remaining piece that needed an explicit hand.
- **Log page readability.** The Log already had 112 entries and only grows -- previously one flat, ungrouped, unpaginated list, ranked the least scannable screen in the audit. `LogPage.jsx` now groups consecutive entries sharing a calendar day (in the viewer's own local time) under one heading, and shows only the 40 most recent entries at a time with a "Show N more" button revealing the rest in the same page-size increments -- purely a client-side slice of the array `getActivity()` already returns in one call (the backend's existing `listGlobalActivity(limit = 300)` needed no change), so no new endpoint or pagination protocol was needed. Grouping by day also let each row's own timestamp shrink from a full date-plus-time string to just the time, since the day heading now carries the date -- removing a redundant repetition on every single row, not just adding a heading.
- **Space page layout & the Graph's fixed width.** The Space page's own metadata (status, accent picker, working-toward, due date, tags, promotion, Categories) previously sat as six bare one-line rows directly under the title, unlike the well-organized cards everywhere else in the app -- now grouped into one bordered `.space-details-panel` (same surface/border/radius family as `.view-card`/`.digest`/`.work-block`), so it reads as one considered section instead of loose metadata. (This panel was later made into a native `<details>` for adaptive density -- see the Interaction & Workflow pass below.) Separately, `#root`'s app-wide 900px content column was actively clipping node labels on the Map, not just leaving unused space elsewhere -- traced to the graph canvas's own fixed logical coordinate space (`WIDTH`/`HEIGHT` in `GraphView.jsx`, an SVG `viewBox` clips anything drawn past its bounds by default) rather than the surrounding CSS, so the real fix widened both together: `WIDTH`/`HEIGHT` went from 640x440 to 900x620 (same ~1.45 aspect ratio, more logical room for a node's label before it can reach the edge), paired with a new `.graph-frame`/`.graph-frame-inner` wrapper on `GraphPage.jsx` that breaks just the canvas out of the centered column via the standard `calc(50% - 50vw)` negative-margin technique (capped at 1400px, not full-bleed to the viewport edge) -- every other page, and the rest of the Graph page itself (heading, the Relational Space form below the canvas), stays at the ordinary 900px width, since prose reads fine there and this was never a blanket "everything should be wider" ask. The physics loop's own force/spring/damping calculations were deliberately left untouched -- only the two size constants they already read from changed, the same caution the professionalism pass's correctness-fixes slice already showed toward this file.

Verified live end-to-end, not just by re-reading the diff: `vite build` and the full frontend (`npx vitest run`, 295 tests, 4 new -- two covering the Log's day-grouping and pagination, one confirming the Space page's details panel groups the expected fields, one confirming the Graph's canvas renders inside the new wide frame) and backend (191 tests, unaffected) suites all pass, `oxlint` shows the same pre-existing warnings only, and every affected page was re-screenshotted afterward and visually diffed against the pre-pass captures -- the Dashboard and Insights pages render pixel-identical (confirming the token/radius consolidation changed no visible sizing), the Space page's metadata now reads as one clear section, and the Graph's node labels render fully within the canvas with no horizontal-scrollbar side effect from the breakout technique (checked directly via `document.documentElement.scrollWidth`).

## Data model, current state
- `spaces` — id, title, template_id (nullable), status, tags (JSON array — Resources and any future category *of Spaces*), goal (nullable text — "what this Space is working toward," a property of the Space itself, not its content), categories (JSON array of freely-named facets *of this Space's own topic*, e.g. "Financial Impact" — see the Categories vocabulary entry above; distinct from tags), accent (nullable text, one of `star`/`underline`/`triangle`/`dot` — Visual Identity's manual accent layer, see Visual direction above; null means none picked), origin (nullable text, `'external'` | `'internal'` — Provenance, see the vocabulary entry above; set once at creation by `CreateResource.jsx`/`CreateSynthesis.jsx`, null for an ordinary Space, never edited afterward), due_date (nullable text, `'YYYY-MM-DD'` — a real target date for the Space as a whole, see the Time vocabulary entry above; distinct from a List item's own `reviewBy`, which means "come back and reconsider this," not "this is due"), created_at, updated_at
- `blocks` — id, space_id, type, content (JSON), properties (JSON — status-like markers: `skeletonLane`, `skeletonRole`, `categories` (a JSON array of the Space's own Category names this block belongs to, many-to-many), `workspaces` (a JSON array of Workspace ids this block has been assembled into, many-to-many, ids rather than names since a Workspace is a real row that can be renamed/deleted independently), and `projectId` (a single nullable Project id, not an array -- a Milestone or Session belongs to at most one Project at a time)), position, created_at, updated_at
- `workspaces` — id, space_id (a Workspace belongs to exactly one Space, same as a block), name, created_at, updated_at — a deliberately assembled, named environment; see the Workspaces vocabulary entry above
- `projects` — id, space_id (a Project belongs to exactly one Space, same shape as `workspaces`), name, created_at, updated_at — a real, named goal/project a Milestone or Session belongs to; see the Projects vocabulary entry above
- `templates` — id, name, block_arrangement (JSON)
- `resource_templates` — id, type (unique, matches a Resource's own type tag), label, facets (JSON array of `{name, prompt}`) — a deliberately separate mechanism from `templates` above; see the Resources vocabulary entry above
- `trail_entries` — id, space_id, kind (auto/manual/review — `review` added for the Time arc's Review layer, see the Time vocabulary entry above), summary, note, skeleton_snapshot (JSON), created_at — no longer write-once: `updateTrailEntry` in `backend/src/db/queries.js` lets `note` (and, for a `manual` entry, its recomputed `summary`) be edited after creation; `kind` and `skeleton_snapshot` stay fixed at write time, since a snapshot is a historical fact about that moment, not something later editing should touch.
- `activity_log` — id, space_id (nullable, no foreign key), space_title (snapshotted at write time, since a "Space deleted" entry must survive the Space itself being gone), kind, summary, created_at — the Log's structural-event half; merged with `trail_entries` at query time by `listGlobalActivity`, not duplicated into this table
- References are blocks of type `reference` with a `target_space_id` in their content — indexed, since backlinks and the Relational Map query it constantly.
- A Text block's content is `{lines: [{id, text, tag}]}` — each line has a stable id and its own attribution tag, independent of every other line (see the Tools vocabulary entry above). Comparison's embedded text-kind sides keep the older `{tag, text}` shape forever, since they're plain objects inside a `comparison` block's own content, never real `type='text'` rows.
- A Tensions-lane List item can carry `statementA`/`statementB`, each `{blockId, itemId}` pointing at an item in one of the other three Skeleton lanes' blocks — resolved live at read time (see the Skeleton entry above), not snapshotted or duplicated.
- A Work block's content is `{statement, support, confidence}`, where `support` is a JSON array of `{id, text}` (a free-text point) or `{id, pointer: {blockId, itemId}}` (a live link to another claim -- `itemId` null means the pointer targets a whole Work block's own statement, set means it targets a specific Skeleton lane item, same shape a Tension's own pointers use). `backend/src/db/queries.js`'s `WORK_TYPES` is the one list of which block types `listWorkItems()` (and so Synthesis's picker) draws from — see the Work vocabulary entry above. Synthesis itself needed no schema change at all: it's just `createSpace`'s existing `tags`/`extraBlocks` parameters, the same ones Resource creation already uses.
- A Milestone block's content is `{label, targetDate, reached, reachedAt, note}` — `targetDate`/`reachedAt` are nullable `'YYYY-MM-DD'` text, `reached` is a plain boolean toggled directly (setting `reachedAt` to today when turned on, clearing it when turned off). See the Time vocabulary entry above.
- A Session block's content is `{label, startedAt, endedAt, durationMinutes, note}` — `startedAt`/`endedAt` are nullable ISO datetime text (client clock, set by Start/Stop), `durationMinutes` is a plain integer computed and stored at Stop time. A session is "running" whenever `startedAt` is set and `endedAt` isn't; elapsed time while running is always derived from `startedAt`, never stored separately. See the Time vocabulary entry above.
- A List item's and a Work item's `confidence` field share one 5-value scale, `questioned`/`tentative`/`moderate`/`solid`/`certain`, defined once as `CONFIDENCE_LEVELS` in `frontend/src/registry/blocks.js` (List's own `CONFIDENCE_CYCLE` in `frontend/src/blocks/listItems.js` mirrors it, kept as a separate export since other code already imports from there).
- Tags are queried by membership (`listSpacesByTag` in `backend/src/db/queries.js`, `GET /api/spaces?tag=...`) — general-purpose, not written specifically for Resources.
- A block's Categories are edited independently from its content via `updateBlockCategories` in `backend/src/db/queries.js` (PATCH `/blocks/:id` accepts `content` and/or `categories`, since they're independent edits) — kept separate from `updateBlockContent` because Categories are a property/attribute of the block, not its actual content.
- A block's Workspace membership is edited the same independent way, via `updateBlockWorkspaces` (PATCH `/blocks/:id` also accepts `workspaces`, any subset of `content`/`categories`/`workspaces` together).
- A Milestone/Session's Project membership is edited the same independent way, via `updateBlockProject` (PATCH `/blocks/:id` also accepts `projectId`, alongside any subset of `content`/`categories`/`workspaces`/`projectId`) -- a single id or `null`, not an array.
- `createSpace` (and `createSpaceWithSetup`/`POST /spaces` on top of it) accepts an optional `categories` array at creation time, alongside the existing `tags` — used by `CreateResource.jsx` to seed a new Resource's four starting facets before any block exists; an ordinary Space creation still leaves this empty and adds Categories later from the Space page, same as before.
- `createSpaceWithSetup` also accepts an optional `workspaces` array (plain names) — used by `CreateSpace.jsx`'s Workspaces step. Each is created via `createWorkspace` right after the Space itself, before `extraBlocks` are added, specifically so a block spec carrying `properties.workspaceNames` (draft-time names) can be resolved into real `properties.workspaces` (ids) in the same request.

Propose refinements to this if something better fits once more building happens — it's a foundation, not gospel.

## Transparency / indexability requirement
Every Tool — every Block type and every View type — must be registered in one single, readable file each (`frontend/src/registry/blocks.js`, `frontend/src/registry/views.js`) — never scattered across the codebase. The point is that the person can open one file and see the complete list of what exists; the planned Tools catalog page makes this visible *in the app itself*, not just in the source. Keep all cross-Space queries (counts, status distribution, backlink lookups, tag membership) going through a small, consistent set of query functions imported from `backend/src/db/queries.js` rather than ad hoc SQL sprinkled around — this is what makes Dashboard metrics and things like the Resources digest buildable without new plumbing. As of the organization pass (see Roadmap), `queries.js` itself is a thin barrel re-exporting from `backend/src/db/queries/*.js` — one small file per concern (Spaces, Blocks, Workspaces, Skeleton, Trail, Review, Work, the Log, Insights, Reports, Dashboard aggregations) — rather than one ~1,800-line file; every route still imports from `queries.js` and never reaches into a `queries/*.js` file directly, so the "one entry point" property this section asks for is unchanged, it's just backed by readable per-concern files instead of one large one.
